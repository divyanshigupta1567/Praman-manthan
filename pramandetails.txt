1. How Praman Works
Praman turns individual citizen complaints into an early-warning picture of what's happening across a city. A single
complaint about a pothole doesn't tell you much on its own — but twelve similar complaints from the same
neighbourhood in three days does. Praman's job is to notice that automatically.
The pipeline, stage by stage:
1. Citizen submits a complaint — A short description, a location (map pin or manual lat/lng), and an optional photo. No category
selection needed — the system predicts it.
2. AI Classification — The complaint text is run through a trained classifier that predicts one of six categories (Pothole, Garbage,
Water Leakage, Streetlight, Sewage, Traffic Hazard) with a confidence score.
3. Text Similarity — The complaint is compared against other recent complaints in the same category using TF-IDF + cosine
similarity, to see if it describes something already reported.
4. Geographic Proximity — Haversine distance checks which nearby complaints (within ~1-2 km) could plausibly be the same
real-world issue.
5. Incident Clustering — Complaints that are similar in category, text, location, and time get grouped into a single incident — the
shift from counting complaints to recognising a pattern.
6. Time Aggregation & Spike Detection — Daily complaint volume per category/area is compared against a rolling baseline. A
statistically unusual jump (z-score) marks an incident as emerging.
7. Pressure Score — Each incident gets a 0-100 score combining how sharp the spike is, how large the cluster is, how long it's
been active, and how much of it remains unresolved.
8. Auto-Escalation — Incidents crossing a high-pressure threshold are automatically flagged at the top of the dashboard — no
one has to notice manually.
9. Authority Dashboard — The civic team sees KPIs, a map of hotspots, evidence for every flagged incident, and a daily briefing
generated purely from the computed numbers above.
The core distinction that makes this work: a complaint is one citizen's report; an incident is a pattern discovered
across many complaints. Twenty-five complaints might resolve into four separate incidents once similarity, location, and
time are considered — that's the actual intelligence layer, not just a filtered list.

4. Starter Prompts — Role-Wise
Copy the relevant block into your AI coding assistant to kick off your module. Each one assumes the shared schema
below is fixed first — paste the schema alongside the prompt if your assistant hasn't seen it yet.
Member 1 — ML & Dataset
I'm building the ML module for a civic incident-intelligence hackathon project (Praman).
Task 1 — scripts/generate_data.py:
Generate 500-1000 synthetic citizen complaints as CSV with columns:
complaint_id, complaint_text, category, latitude, longitude, locality, timestamp, status.
Categories: Pothole, Garbage, Water Leakage, Streetlight, Sewage, Traffic Hazard.
Use 6-10 generic area names (Area A, Area B, ...). Spread timestamps over 4-6 weeks.
Use a fixed random seed. Write 4-6 text templates per category with slot variables for
natural variation. Deliberately seed 2-3 scripted spikes (one category+area+3-day window
gets 4-6x normal volume) and 15-20 near-duplicate complaints (same locality, close
timestamps, minor wording changes).
Task 2 — ml/classifier.py:
Train a TF-IDF + Logistic Regression classifier on complaint_text -> category, with a
Linear SVM as a comparison model. Do a train/test split and compute real Accuracy,
Precision, Recall, F1 (no hardcoded numbers). Output predicted_category + confidence
per complaint, plus a metrics dict for both models.
Member 2 — Incident Intelligence
I'm building the spike-detection and scoring module for a civic hackathon project (Praman).
Input: a list of incident cluster objects, each with complaint_count per day, first_seen,
last_seen, and unresolved_count (schema attached).
Task 1 — ml/anomaly.py:
For each category+locality, compute a rolling 7-day mean and std of daily complaint volume.
Compute z = (current - rolling_mean) / rolling_std. If fewer than 5 prior days exist, mark
insufficient_history=true instead of computing z. If rolling_std == 0, set z=0 when current
equals baseline, else cap z at 3. Compute spike_pct = ((current-baseline)/baseline)*100,
returning 'N/A (new activity)' if baseline == 0.
Task 2 — ml/pressure.py:
Normalize to 0-100: spike = min(100, z/3*100), size = min(100, complaint_count/30*100),
duration = min(100, hours_since_first_seen/72*100), unresolved = unresolved_count/
complaint_count*100. Combine as 0.4*spike + 0.3*size + 0.2*duration + 0.1*unresolved.
Apply bands: 0-59 Normal, 60-79 Emerging, 80-100 High Pressure (auto_escalated=true).
Member 3 — Clustering
I'm building the incident-clustering module for a civic hackathon project (Praman).
Input: a list of complaints, each with complaint_text, category, latitude, longitude,
timestamp (schema attached).
Task 1 — ml/similarity.py:
Compute TF-IDF + cosine similarity between complaints within the same category.
Label pairs >=0.85 as 'Potential Duplicate', 0.55-0.85 as 'Potentially Related',
below 0.55 as unrelated.
Task 2 — Haversine distance function between two lat/lng points in km.
Task 3 — ml/clustering.py:
Build a graph per category: an edge between two complaints exists if similarity >= 0.55,
Haversine distance <= 2 km, and timestamps are within 72 hours of each other. Run
connected-components (networkx or manual union-find). Keep components with >=3 complaints
as incident clusters. Compute centroid (mean lat/lng), cluster_radius_km (max distance to
centroid), complaint_count, similar_complaint_count, unresolved_count, first_seen, last_seen.
Output objects matching the incident cluster schema exactly.
